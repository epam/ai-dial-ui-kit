2. First run: two false positives, not a real defect

`npm run fixtures:run-all` reported:

Both failures turned out to be bugs in the new/upgraded test fixtures
themselves, not in @epam/ai-dial-ui-kit:

(a) consumer-esm's own `src/main.tsx` JSDoc comment literally listed every
    forbidden marker string ("exclude ag-grid-community, ag-grid-react,
    @monaco-editor/react, monaco-editor, @uiw/react-md-editor, and
    @uiw/react-markdown-preview"). With `minify: false` (required so
    assert-static-graph.mjs's content-grep signal can inspect real output),
    esbuild/Vite 8 + @vitejs/plugin-react 6 preserves that comment verbatim
    in the emitted chunk (`dist/assets/index-*.js:16757-16758` in the
    reproduced build) - so the assertion tripped on its own documentation,
    not on any bundled dependency. Confirmed by direct grep: `ModuleRegistry`,
    `AllCommunityModule`, and `AgGridReact` (the *implementation* markers)
    were absent from that chunk; only the six literal package-name strings
    from the comment were present, both on the same two lines. Fixed by
    rewording the comment to describe the requirement generically ("AG Grid
    and every editor-only (Monaco / `@uiw/*`) dependency") instead of
    spelling out the exact specifiers the assertion checks for.

(b) consumer-mixed-grid's `--dynamic-after Button:ag-grid-community` check
    used `Button` as the "parent" marker. `Button` is not in
    assert-static-graph.mjs's MARKERS map, so it fell back to a literal
    content-grep for the bare word "Button" - which also matches AG Grid's
    own bundled UI code (`FilterButton`, `enableFilterButton`, etc. - 185
    occurrences confirmed via direct grep in the dynamic Grid chunk). That
    made the dynamic Grid chunk itself register as a "parent" hit, which
    trivially put it inside its own static closure and failed the nested-
    boundary check. Fixed by switching the parent marker to
    `load-grid-trigger` (the fixture's own DOM element id: unique to the
    eager static chunk, confirmed 2 hits there / 0 hits in the Grid chunk).

5. Conclusion answering design.md's first Open Question
------------------------------------------------------------
**The root-barrel import-then-export topology
(`dist/dial-ui-kit.js:30-32,155-158,239,313-314`, unchanged by this
diagnosis - no source edits were made) is NOT, by itself, an obstacle to
correct tree-shaking in a real Vite 8 / Rolldown-style downstream build.**
Both the pre-existing root-only scenario (consumer-esm) and the new mixed
eager-root + lazy-`./grid` scenario (consumer-mixed-grid) tree-shake AG Grid
out of the static graph correctly today, using the package's CURRENT,
unmodified build output, as long as the consumer applies no manual chunking
override.

This shifts the primary suspect for the measured `ai-dial-chat` regression
towards Decision 5's finding in design.md's Context section:
`apps/chat/vite.config.mts:220-241`'s `manualChunks` rule, which forces every
non-editor `@epam/ai-dial-ui-kit` module - Grid included - into one named
`ui-kit` chunk regardless of reachability. That rule was out of scope to
change from this repository and was not touched here. Section 3's root-
topology restructuring (tasks.md 3.1-3.3) is downgraded from "required" to
"conditional, pending Section 7's ai-dial-chat dual-manualChunks
measurement" - it should not be undertaken as ai-dial-ui-kit source changes
until that measurement (with the consumer's manualChunks override actually
disabled) confirms whether any package-level gap remains once the known
consumer-side cause is accounted for.

Decision 3 (relocate `ModuleRegistry.registerModules` out of module scope)
remains worth doing regardless of this finding - it is independently
motivated as side-effect hygiene, not solely as a tree-shaking fix, per
design.md's own reasoning.

Section 9 — reopened follow-up: root lazy editor loader retains Grid (2026-09-08)
====================================================================================
The consumer (`ai-dial-chat`) side of this whole investigation continued in a
separate, active `ai-dial-chat` change (`complete-chat-cold-load-integration`).
During its own real-consumer verification it found a fourth, genuinely
package-level defect this change's earlier sections had not covered: a
minimal Vite 8.0.16 reproduction with an eager root `Button` + a *retained*
(not merely imported-and-unused) root `LazyMarkdownEditor` loader + `Grid`
reached only via a separate dynamically-imported module still pulled AG
Grid into the initial graph. Their `verification-report.md` (in
`ai-dial-chat`) documents the exact reproduction, byte counts, and their
finding that switching the loader import to `@epam/ai-dial-ui-kit/editors`
avoided it. They amended this change's own `tasks.md` (adding this Section
9), `specs/package-distribution/spec.md`, and `verification-report.md`
in place before handing the actual package-level fix back to this repo.

1. Reproduction, confirmed
---------------------------
Built `fixtures/consumer-mixed-grid-editor-loader`: eager `Button` +
`Object.assign(window, { Button, LazyDialJsonEditor, LazyDialMarkdownEditor,
LazyMarkdownEditor })` (genuine retention a bundler cannot tree-shake away,
unlike an unused reference) + `Grid` reached only via
`import('./grid-feature')`, a separate local module statically importing
`Grid` from `@epam/ai-dial-ui-kit/grid`.

- Against `vite: ^8.0.0` (resolved 8.2.2 at the time): PASSED cleanly - no
  reproduction. This matches Section 2's original diagnosis and is why the
  defect was missed earlier.
- Against `vite: 8.0.16` exactly (the version `ai-dial-chat`'s own
  `verification-report.md` said it measured with, and the version its root
  `package.json`'s `^8.0.0` range could still resolve to on an older
  install): FAILED. Static chunk `index-*.js` grew to 2,193,440 bytes raw /
  525,880 bytes gzip and contained `ag-grid-community`/`ag-grid-react`
  (confirmed via `assert-static-graph.mjs`'s module-id and content-grep
  signals, not filename guessing) - matching the magnitude of `ai-dial-chat`'s
  own reported 417,119 gzip byte leak. This is a genuine Vite/Rolldown-
  version-dependent automatic-chunking behavior difference, not a fixture
  artifact: same source, same package, different bundler patch version,
  different result.

2. Root cause
-------------
`src/index.ts` declared `LazyDialJsonEditor`, `LazyDialMarkdownEditor`, and
`LazyMarkdownEditor` as inline `export const LazyX = () => import('./path')`
statements directly inside the root barrel file - and `src/subpaths/editors.ts`
declared its own separate, textually-duplicated copies of the same three
functions (each with an identical `import()` call to the same target
module), by design, to keep the manifest generator's inline-pattern
detection working (see below). This meant `dist/dial-ui-kit.js` (the root
entry) and `dist/editors.js` each carried their own independent physical
copy of each loader's function body - and each loader body's own `import()`
call gave the *root entry itself* an outgoing dynamic-import edge, not just
the `./editors` entry.

In Rolldown 8.0.16's automatic chunk-splitting, when the eager root
(`dial-ui-kit.js`, needed for `Button`) carries its own dynamic-import edges
(from the retained `LazyMarkdownEditor`'s body) *and* a completely separate
part of the consumer graph (`grid-feature.tsx` → `grid.js`) also needs
Grid/AG Grid, the automatic chunker in that version merged everything -
Button, the editor loaders, Grid, AG Grid - into one shared static chunk.
8.2.2 does not exhibit this; the exact Rolldown change between these
versions was not investigated further (out of scope - the fix targets the
package's own topology so it does not depend on which side of that Rolldown
behavior a consumer's installed version happens to be on).

3. Fix
------
Extracted each loader into its own shared leaf module, so root and
`./editors` reference the *same* emitted chunk instead of each duplicating
the loader's own `import()` call inline:

- `src/components/JsonEditor/lazy.ts` → `LazyDialJsonEditor`
- `src/components/MarkdownEditor/lazy.ts` → `LazyDialMarkdownEditor`
- `src/components/New/MarkdownEditor/lazy.ts` → `LazyMarkdownEditor`

`src/index.ts` and `src/subpaths/editors.ts` now both
`export { LazyX } from '<leaf module path>'`. Confirmed via
`dist/dial-ui-kit.js`/`dist/editors.js` grep: both entries import the exact
same physical file (`./components/New/MarkdownEditor/lazy.js`), not two
copies.

`src/mcp/generate-manifest.ts` (the MCP component-manifest generator)
previously only recognized the inline `export const LazyX = () =>
import(...)` shape directly inside `src/index.ts`. It now also follows a
`export { LazyX } from './leaf'` re-export to the leaf module and extracts
the identical metadata from the declaration found there (new helpers
`extractLazyLoaderFromDecl`/`findExportedVariableDecl`, shared by both the
inline and re-export code paths). Verified the regenerated manifest still
attaches the correct `lazy: { loaderExportName, ... }` metadata to
`DialJsonEditor`, `DialMarkdownEditor`, and `MarkdownEditor` (2.0) -
byte-identical Next.js dynamic-import example snippets, same 162-component
count.

Re-ran the exact failing reproduction against Vite 8.0.16 after the fix:
static chunk dropped to 724,360 bytes raw / 145,660 bytes gzip, AG Grid and
`@uiw/*` fully excluded from static and confined to their dynamic chunks
(`assert-static-graph.mjs` PASS). Also re-tested with all three loaders
retained simultaneously, and with the loaders imported from `./editors`
instead of root (`fixtures/consumer-mixed-grid-editors-subpath`) - both
pass, on both Vite versions.

4. Test-fixture bugs found and fixed along the way (none are product defects)
------------------------------------------------------------------------------
- `--forbidden-everywhere` used for `@uiw/*`/monaco on a fixture that
  legitimately, lazily loads them (once all three loaders are retained)
  produced a false FAIL - switched those checks to `--dynamic-require`.
  Package behavior was already correct; only the assertion was wrong.
- Vite's own `vite/preload-helper` runtime (injected once a fixture has more
  than one dynamic-import chunk) calls `fetch()` on every
  `<link rel="modulepreload">` tag; jsdom has no real HTTP server, so this
  crashed the smoke test with ECONNREFUSED. Stubbed `fetch` as a no-op
  `Response`, matching the existing `ResizeObserver`/`matchMedia` stub
  pattern.
- Invoking `LazyDialJsonEditor`/`LazyDialMarkdownEditor`/`LazyMarkdownEditor`
  directly from a bare top-level Node script (outside any React
  event/lifecycle) hangs indefinitely for reasons unrelated to this fix
  (confirmed: the identical call resolves and renders fine from inside a
  React click handler). Smoke tests now only verify the loaders are
  *retained as real function references*, not invoke them directly from the
  script; the actual editor-rendering runtime path is already covered by
  the library's own Vitest suite.
- `fixtures/consumer-markdown-editor`'s stricter nested-boundary check
  (`--dynamic-after MarkdownEditorContainer:monaco-editor`) started failing
  independent of any change in this session - confirmed via a controlled
  `git stash` test against completely unmodified upstream source. A
  transitive `@monaco-editor/loader`/`monaco-editor` patch bump changed
  Rollup's automatic chunk consolidation so Monaco now merges directly into
  `MarkdownEditorContainer`'s own already-dynamic chunk instead of a nested
  one one hop further. The requirement that actually matters (Monaco absent
  from the static graph, present only dynamically) is unaffected and still
  asserted; the overly specific nested-hop assumption was dropped. This is
  pre-existing dependency drift, unrelated to Section 9 or anything else in
  this change.

5. `assert-static-graph.mjs` strengthened (addresses task 9.4)
-----------------------------------------------------------------
Added two capabilities, independent of the pass/fail package checks:
- Cross-checks every `--forbidden`/`--forbidden-everywhere` package against
  the *actual* `index.html` `<script type="module">`/`<link
  rel="modulepreload">` entries (parsed directly, not inferred from
  Rollup's own `imports`/`isEntry` metadata) - a genuinely independent
  second signal for "what a real browser fetches on load," and fails if
  HTML and the graph-report closure disagree about what counts as initial.
- Always reports the static closure's initial JS/CSS raw and gzip byte
  totals, measured independently of each other.
